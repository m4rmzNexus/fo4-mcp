# OS-09 — Job-provenance + path-desync guard for the Tier-3 in-game runner

**verdict:** confirmed-open | **effort:** M | **risk:** low | **recommend_now:** True

**area:** in-game testing infra

## What's missing
The native plugin hardcodes absolute job/diag paths (R"(C:\Modding\fo4-mcp\...)") while Python derives them from cfg.tools_dir; a repo move (already happened once) or cfg override silently falls back to the built-in DefaultJob and the test 'passes' running the wrong commands. Python also never confirms the diag's '[job] loaded: N resolves, M cmds' matches the rendered spec, so a stale/missing job degrades to false-positive 'sequence_completed'.

Both halves verified against source.
PLUGIN HARDCODES ABSOLUTE PATHS: tools/commonlibf4-template/src/main.cpp:54-55 — `kJobPath = R"(C:\Modding\fo4-mcp\tools\commonlibf4-template\ingame-job.txt)"` and `kDiagPath = R"(...runner-diag.log)"`. Compiled into the DLL, not derivable at runtime.

So FO4_REPO_ROOT/FO4_TOOLS_DIR override, or a repo move, makes Python write a path the DLL does not read. MEMORY confirms the repo already moved once (to C:\Modding).

Grep across **/*.py for jobid|job_confirmed|[job] loaded: returns zero hits — no provenance check exists today.

## Concrete plan

1. PLUGIN main.cpp LoadJob() — parse a new optional `jobid <token>` verb. Add a `std::string jobId;` field to struct Job (after line 97). In the getline loop (main.cpp:133-185) add `else if (verb == "jobid") { is >> j.jobId; }`. This is purely additive; unknown verbs are already ignored, so an old DLL with a new job file still works and vice-versa.
2. PLUGIN main.cpp LoadJob() success diag — change the snprintf at main.cpp:187-189 to include the job id, e.g. append ` jobid=%s` and pass `j.jobId.empty() ? "-" : j.jobId.c_str()`. Keep the existing `[job] loaded: %d resolves, %d cmds` prefix BYTE-FOR-BYTE so the new Python parser regex `\[job\] loaded: (\d+) resolves, (\d+) cmds` still matches. The `[job] no job file` line (main.cpp:127) already exists — no plugin change needed for the no-file case.
3. PLUGIN: rebuild + redeploy the DLL via the existing xmake toolchain (tools/commonlibf4-template) into the MO2 mod folder. This is the one non-pure step; it is a local compiled-artifact build (no Steam Data write). Keep the diag/job paths hardcoded — fixing the path itself is out of scope; the sentinel turns a silent desync into a loud failure regardless of where the paths point.
4. PYTHON ingame_test.py render_job() — generate a per-run uuid and write it as the FIRST data line after the header comment. In render_job add `import uuid` (top of file) and `job_id = uuid.uuid4().hex`; emit `lines = ["# ...", f"jobid {job_id}", save_line]` (line 157). Return the id to the caller: change render_job to also surface it — simplest is to compute job_id in fo4_run_ingame_test (line 256) and inject it into spec-independent rendering, OR have render_job return (text, job_id). Prefer computing job_id in fo4_run_ingame_test and passing it into a small `render_job(spec, job_id=...)` kwarg so the renderer stays pure/testable.
5. PYTHON ingame_test.py fo4_run_ingame_test() post-run parse (after diag_text is read at line 341). Add: (a) `job_loaded = re.search(r"\[job\] loaded: (\d+) resolves, (\d+) cmds", diag_text)`; (b) `no_job_file = "[job] no job file" in diag_text`; (c) `jobid_echoed = f"jobid={job_id}" in diag_text` (matched against the diag's `[job] loaded: ... jobid=<hex>` line). Compute `n_res, n_cmd` from `len(res_lines-equivalent)` — i.e. `len(spec.get('resolves') or [])` and `len(spec['commands'])` (already validated). Set `job_confirmed = bool(job_loaded) and not no_job_file and jobid_echoed and int(job_loaded.group(1))==expected_resolves and int(job_loaded.group(2))==expected_cmds`.
6. PYTHON ingame_test.py success folding — change BOTH branches at lines 367-370 to require provenance: `success = appeared and bool(papyrus_matches) and job_confirmed` (pattern branch) and `success = appeared and exited and sequence_completed and job_confirmed` (no-pattern branch). Add to the returned dict (lines 372-388): `"job_id": job_id, "job_confirmed": job_confirmed, "job_no_file": no_job_file, "job_loaded_resolves": int(job_loaded.group(1)) if job_loaded else None, "job_loaded_cmds": int(job_loaded.group(2)) if job_loaded else None`. When `no_job_file` is True or counts mismatch, success is False and the diag_tail + job_no_file flag explain why loudly.
7. PYTHON ingame_test.py dry_run plan — add `"job_id": job_id` and `"job_text"` already contains the `jobid` line, so the dry_run output self-documents the sentinel. No success logic runs in dry_run, so no further change there.

## Test strategy
Pure-Python, no game launch — fits the existing monkeypatched suite in mcp-server/tests/test_tools_ingame_test.py.
1) render_job: assert the rendered job contains a `jobid <hex>` line as the first non-comment line, and that the returned/derived job_id is a 32-char hex (extend test_render_default_mcploop).
2) JOB-CONFIRMED HAPPY PATH: extend test_execute_success_with_papyrus_match — capture the job_id by reading the written ingame-job.txt (already asserted to exist at line 245), then write a diag containing `[job] loaded: 1 resolves, 1 cmds, ... jobid=<that id>` plus `[seq] UI: qqq`. Assert out['data']['job_confirmed'] is True and success True.
3) DESYNC / NO-FILE FALSE-POSITIVE GUARD (the core new test): diag contains `[job] no job file; using built-in default (MCPLoopTest)` and `[seq] UI: qqq` (exactly what DefaultJob produces). Assert success is False, job_confirmed False, job_no_file True — proving the wrong-job run no longer passes. This directly reproduces the bug.
4) STALE-JOB / COUNT-MISMATCH: diag has `[job] loaded: 1 resolves, 1 cmds ... jobid=<DIFFERENT-uuid>` (a previous run's job). Assert job_confirmed False (jobid mismatch) and success False.
5) COUNT-MISMATCH same-id: diag has correct jobid but `[job] loaded: 1 resolves, 0 cmds` while spec has 2 cmds. Assert job_confirmed False.
6) Regression: re-run full suite (currently ~402 tests per MEMORY) to confirm no break in render/validation/navtest tests. The plugin C++ change is validated offline by rebuilding; an in-game re-run is the user-gated live step (matches the existing Tier-3 'live CK/game = user-trigger' rule) and is NOT required to land the Python guard, since the guard's whole point is to make a future bad live run fail loudly rather than silently pass.


## Blockers / scope notes
None for the Python guard (fully autonomous, pure, test-covered, no Steam/Data writes). One soft dependency: the `job_confirmed` flag only goes live in-game after the DLL is rebuilt to echo `jobid=` into runner-diag.log. The DLL rebuild uses the existing local xmake/MSVC toolchain (tools/commonlibf4-template) and writes only to the MO2 mod folder, not the Steam Data dir — so it stays inside the safe-write boundary. Until the DLL ships, an OLD DLL will not echo the jobid, which would make job_confirmed=False and FAIL a real run; to avoid breaking the proven pipeline before redeploy, gate the jobid-echo requirement so that if NO `[job] loaded:` line is found at all (old DLL) the tool falls back to the legacy success rule with a `job_confirmed: null` + explicit warning, but if `[job] no job file` IS present it always fails. Land Python first behind that compatibility shim, then rebuild+redeploy the DLL, then tighten to require the echo.
