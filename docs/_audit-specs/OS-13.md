# OS-13 — GetIsAliasRef param render fix + full INFO fragment/link readback in dialogue-dump

**verdict:** confirmed-open | **effort:** S | **risk:** low | **recommend_now:** True

**area:** quest + dialogue

## What's missing
GetIsAliasRef alias-slot conditions display a spurious FormKey (param1 read via ParameterOneRecord.FormKeyNullable instead of the number/alias slot), so authored alias conditions look wrong on dump. The dump also can't read back INFO fragments (scriptName/fragmentName/onBegin/onEnd) or link/scene fields, so OS-04/OS-16 can't be verified.

## Evidence (code-grounded)
Both halves confirmed against live Mutagen 0.53.1 API (reflection-probed) + the source.

PART 1 — GetIsAliasRef param mis-render (REAL):
- tools/mutagen-cli/src/Program.cs:543 renders param1 unconditionally via the Form slot: `param1 = c.Data is IFunctionConditionDataGetter f2 ? $"{f2.ParameterOneRecord.FormKeyNullable}" : null`.
- SetParam (Program.cs:903-921) routes a param by shape: a ':'-bearing key -> ParameterOneRecord.SetTo(fk); an int -> ParameterOneNumber; else ParameterOneString. These are 3 overlapping views of ONE packed condition slot.
- IFunctionConditionDataGetter exposes ParameterOneNumber(Int32), ParameterOneRecord(IFormLinkGetter), ParameterOneString(String) (probe-confirmed).
- Condition.GetParameterTypes(Function) returns a 3-tuple of Condition.ParameterType; GetIsAliasRef => (Alias, None, None); GetIsID => (ReferencableObject,..); GetStage => (Quest,..). So GetIsAliasRef param1 is an Alias = NUMBER slot.
- Probe proof: a FunctionConditionData{Function=GetIsAliasRef, ParameterOneNumber=4} renders ParameterOneRecord.FormKeyNullable as 'Null' — the dump hides the real alias index 4 (or shows a spurious FormID off the overlapping bytes when read from a real binary).
- Documented at docs/fo4-quest-dialogue-system.md:121-124 ('the GetIsAliasRef alias index goes in the number/alias slot (ParameterOneNumber/Unknown3), not as a FormKey — and dialogue-dump currently mis-renders that slot as a FormKey') and the backlog row at :346.

PART 2 — INFO fragment/link/scene readback missing (REAL):
- Dump only emits a bare bool: Program.cs:537 `hasFragment = info.VirtualMachineAdapter is not null`. No scriptName/fragmentName/onBegin/onEnd, no link/scene fields.
- API exists (probe-confirmed): IDialogResponsesGetter.VirtualMachineAdapter is IDialogResponsesAdapterGetter -> .ScriptFragments (IScriptFragmentsGetter) with .Script(IScriptEntryGetter.Name), .OnBegin & .OnEnd (each IScriptFragmentGetter -> .ScriptName, .FragmentName). Link/scene fields on the INFO: PreviousDialog, StartScene, StartScenePhase, Topic (all IFormLinkNullableGetter / String).
- Documented as plan P3 at docs/fo4-quest-dialogue-system.md:440-446 ('emit per-INFO setParentQuestStage{onBegin,onEnd}, fragment{onBegin,onEnd scriptName/fragmentName}, and link/scene fields. Also fix the GetIsAliasRef param mis-render').

INFRA: dialogue-dump is a CLI-only verb (Program.cs:46 dispatch, RunDialogueDump at :476); NO Python tool wrapper and NO test invokes it today (grep of mcp-server shows only cell-navmesh-list wrapped). The nearest test analogue is the cell-navmesh-list integration pattern (tools.py:2567 _cell_navmesh_list + test_tools_w12_handoff.py:86). Existing condition/dialogue authoring tests already produce suitable fixtures (test_tools_create_record.py:491 test_create_quest_dialogue_with_conditions).

NOTE: Part 1 is fully independent and shippable now. Part 2's fragment subtree only yields non-null data once INFO-level VMAD authoring exists (OS-04) — the writer today authors quest-level fragments (Program.cs:1961) but NOT INFO fragments (the INFO build loop at 1755-1775 sets Conditions + SetParentQuestStage only). The link/scene part of Part 2 is also independently testable once P4 (Program.cs link resolver) lands, but the dump-side projection can be added now and simply emit null until then.

## Concrete plan

1. In tools/mutagen-cli/src/Program.cs add a static helper `RenderParam(IFunctionConditionDataGetter d, int which)` that calls `Condition.GetParameterTypes(d.Function)`, selects the category for slot `which`, and renders: ParameterType.Alias/Integer/QuestStage/Sex/Axis/Number-like -> the int (ParameterOneNumber/ParameterTwoNumber); String/VariableName -> ParameterOneString; everything Form-like (Actor/ActorBase/Quest/Keyword/Faction/ReferencableObject/Global/etc.) -> ParameterOneRecord.FormKeyNullable?.ToString(); None -> null. Keep it a simple category switch (Number|String|Form|None) by mapping ParameterType->one of those three buckets.
2. Replace Program.cs:543 `param1 = ... f2.ParameterOneRecord.FormKeyNullable ...` with `param1 = c.Data is IFunctionConditionDataGetter f2 ? RenderParam(f2, 1) : null` and add a sibling `param2 = c.Data is IFunctionConditionDataGetter f3 ? RenderParam(f3, 2) : null,` plus surface the alias run-on already authored by BuildCondition: `aliasRunOn = (c.Data as IFunctionConditionDataGetter)?.Unknown3` (the QuestAlias id slot) so GetIsAliasRef-by-runOn is also visible. Also emit `paramType1`/`paramType2` (the GetParameterTypes category string) so a consumer can tell number-vs-form unambiguously.
3. Extend the per-INFO projection (the `infos = dt.Responses.Select(info => new {...})` block, Program.cs:529-547) replacing the bare `hasFragment` with a `fragment` object: when info.VirtualMachineAdapter?.ScriptFragments is non-null, emit `fragment = new { scriptName = sf.Script?.Name, onBegin = sf.OnBegin is {} ob ? new { scriptName = ob.ScriptName, fragmentName = ob.FragmentName } : null, onEnd = sf.OnEnd is {} oe ? new { scriptName = oe.ScriptName, fragmentName = oe.FragmentName } : null }` else null. Keep `hasFragment` for back-compat (cheap bool).
4. In the same INFO projection add link/scene readback fields: `previousDialog = info.PreviousDialog.FormKeyNullable?.ToString()`, `linkTopic = info.Topic.FormKeyNullable?.ToString()`, `startScene = info.StartScene.FormKeyNullable?.ToString()`, `startScenePhase = info.StartScenePhase` (string). These are read-only and emit null today; they light up once P4 authoring lands.
5. Rebuild the CLI: dotnet build -c Release in tools/mutagen-cli/src (net9.0), then copy/refresh the published mutagen-cli the manifest points at (the repo keeps a built copy at tools/mutagen-cli/mutagen-cli.* and src/bin/Release/net9.0/). Do NOT touch any Steam Data folder; all build output stays under tools/.
6. Add a thin Python read-only wrapper `_dialogue_dump(cfg, manifest, plugin, quest)` in mcp-server/fo4_mcp/tools.py mirroring `_cell_navmesh_list` (tools.py:2567): resolve `_mutagen_cli_binary`, run_tool(["dialogue-dump", "--plugin", str(plugin), "--quest", quest], env_extra=_spriggit_env(), timeout=cfg.subprocess_timeout), json.loads(stdout). This is the seam the test calls; no gated write, no new MCP tool surface required unless desired.
7. Add integration tests (see test_strategy) to mcp-server/tests/test_tools_create_record.py next to test_create_quest_dialogue_with_conditions.
8. Update docs/fo4-quest-dialogue-system.md: mark the P3 GetIsAliasRef-render row (:346) and the SNAM/VMAD-dump row (:344) done, and correct the §2.4 note (:121-124) to state the dump now renders the alias index from the number slot via GetParameterTypes.
