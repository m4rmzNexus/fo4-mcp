# OS-04 — INFO Papyrus fragment (TIF VMAD) writer support

**verdict:** confirmed-open | **effort:** M | **risk:** med | **recommend_now:** True

**area:** quest + dialogue

## What's missing
No way for an INFO line to run arbitrary Papyrus (AddItem+Notification+conditional reward). info.VirtualMachineAdapter is read in the dump but never assigned in the INFO build loop. ResponseSpec has no Fragment field. The identical shape already works for QUST and ACTI.

## Evidence (code-grounded)
Gap is REAL today. Single CLI: tools/mutagen-cli/src/Program.cs (Mutagen.Bethesda.Fallout4 v0.53.1, net9).

1) INFO build loop NEVER assigns VirtualMachineAdapter: Program.cs:1726-1776 builds each DialogResponses (info) from a ResponseSpec and sets only Prompt(1729), Speaker(1733), Responses/lines(1742-1752), Conditions(1757-1763), SetParentQuestStage/SNAM(1767-1773). No info.VirtualMachineAdapter assignment anywhere in the loop.

2) ResponseSpec has NO Fragment field: Program.cs:3617-3624 = {Prompt, Speaker, Lines, Conditions, SetParentQuestStage}. The class comment at 3626-3630 even states the TIF VMAD fragment is the deferred P2 path.

3) VirtualMachineAdapter is only READ, never written: dump surfaces it as a boolean at Program.cs:537 (hasFragment = info.VirtualMachineAdapter is not null). The per-record QUST summary (2823-2838) walks topics for topicCount/infoCount/lineCount/conditionCount but has no INFO-fragment count.

4) The 'identical shape already works for QUST/ACTI' claim is TRUE and code-grounded: QUST stage fragments Program.cs:1934-1955 (QuestAdapter{Version=6,ObjectFormat=2}, BuildScriptEntry -> adapter.Script, per-stage QuestScriptFragment{ScriptName,FragmentName}); QUST alias fragments 1964-1985; ACTI 2586-2594. BuildScriptEntry helper at 1039-1058 returns Mutagen.Bethesda.Fallout4.ScriptEntry.

5) Mutagen v0.53.1 API verified by reflection probe (staging/_tifprobe): DialogResponses.VirtualMachineAdapter is settable, type DialogResponsesAdapter{Int16 Version, UInt16 ObjectFormat, ScriptFragments ScriptFragments, ExtendedList Scripts}. ScriptFragments{ScriptEntry Script (settable), ScriptFragment OnBegin, ScriptFragment OnEnd, Byte ExtraBindDataVersion}. ScriptFragment{String ScriptName, String FragmentName}. ScriptFragments.Script type == Mutagen.Bethesda.Fallout4.ScriptEntry (exact same type BuildScriptEntry returns) -> drops in directly.

6) Canonical spec already documented: docs/fo4-quest-dialogue-system.md:169-181 (mechanism B), :425-438 (P2 writer change: 'ResponseSpec.Fragment{ScriptName,OnBegin?,OnEnd?} -> info.VirtualMachineAdapter = new DialogResponsesAdapter{Version=6,ObjectFormat=2}, ScriptFragments with ScriptFragment{ScriptName,FragmentName} on OnEnd/OnBegin, reuse BuildScriptEntry'). Doc line 178-181 explicitly calls it 'missing from the writer — the central gap'.

7) FormID-pinning concern is REAL: INFO is created via new DialogResponses(mod) at 1728, which auto-mints the FormKey (TopicSpec/ResponseSpec carry no explicit FormKey). The TIF class name embeds the 8-hex INFO FormID, so without a pin re-authoring shifts the FormID and orphans the .pex. ctor overload new DialogResponses(FormKey, Fallout4Release) exists for pinning.

## Concrete plan

1. 1. Add spec type in Program.cs near ResponseSpec (after line 3624): class InfoFragmentSpec { string? ScriptName; string? OnBegin; string? OnEnd; string? Flags; List<ScriptPropertySpec>? Properties; }. Mirror FragmentSpec (3437-3443). Add field to ResponseSpec (3617-3624): public InfoFragmentSpec? Fragment { get; set; } with a comment pointing at fo4-quest-dialogue-system.md mechanism B.
2. 2. In the INFO build loop (Program.cs:1764-1775), AFTER the SetParentQuestStage block and BEFORE topic.Responses.Add(info), add: if (resp.Fragment is { } frag) { if (string.IsNullOrWhiteSpace(frag.ScriptName)) return Fail("info fragment missing scriptName"); if (frag.OnBegin is null && frag.OnEnd is null) return Fail("info fragment needs at least one of onBegin/onEnd"); if (!BuildScriptEntry(frag.ScriptName, frag.Flags, frag.Properties, out var fragScript, out var fe)) return Fail(fe); var adapter = new DialogResponsesAdapter { Version = 6, ObjectFormat = 2 }; adapter.ScriptFragments = new ScriptFragments { Script = fragScript }; if (frag.OnBegin is { } ob) adapter.ScriptFragments.OnBegin = new ScriptFragment { ScriptName = frag.ScriptName, FragmentName = ob }; if (frag.OnEnd is { } oe) adapter.ScriptFragments.OnEnd = new ScriptFragment { ScriptName = frag.ScriptName, FragmentName = oe }; info.VirtualMachineAdapter = adapter; } -- exact mirror of QUST 1934-1955, ScriptEntry type-compatible.
3. 3. FormID pinning: add optional string? FormKey to ResponseSpec (and/or TopicSpec). In the loop at 1728, if resp.FormKey is set, parse it (reuse TryKey at e.g. 1732) and create new DialogResponses(parsedFormKey, Fallout4Release.Fallout4) instead of new DialogResponses(mod); else keep new DialogResponses(mod) (back-compat). Validate the pinned ID is in the mod's own load-order slot. This makes TIF_<eid>_<8hex> names stable across re-authoring (doc :435-436).
4. 4. Surface fragment in the per-record QUST summary (Program.cs:2823-2838) for round-trip proof: add ["infoFragmentCount"] = g.DialogTopics.Sum(dt => dt.Responses.Count(rs => rs.VirtualMachineAdapter?.ScriptFragments != null)) and optionally ["infoFragmentScriptName"] = g.DialogTopics.SelectMany(dt => dt.Responses).Select(rs => rs.VirtualMachineAdapter?.ScriptFragments?.OnEnd?.ScriptName ?? rs.VirtualMachineAdapter?.ScriptFragments?.OnBegin?.ScriptName).FirstOrDefault(n => n != null). Keep existing hasFragment dump field at 537.
5. 5. Optional convenience (defer unless trivial): emit a stub .psc at staging/.../Fragments/TopicInfos/TIF_<questEID>_<8hexINFOFormID>.psc with Fragment_Begin/Fragment_End extending Fallout4:Forms (canonical body GetOwningQuest().SetStage(N)). Compilation stays decoupled via fo4_papyrus_build/Caprica (metadata-only contract, same as QUST 1930-1932). The writer only emits VMAD metadata; do NOT couple .pex build into create_record.
6. 6. Rebuild the self-contained CLI (publish, not just build -- per memory apphost/dll gotcha) so mcp-server picks up the new binary, then run the new pytests.
7. 7. Update docs/fo4-quest-dialogue-system.md P2 section status from planned to implemented and add a worked spec example.
